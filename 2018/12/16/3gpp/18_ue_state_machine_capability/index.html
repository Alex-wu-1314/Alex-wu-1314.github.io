    1. UE RRC 状态机概述

    Radio Resource Control（RRC）协议是 NR 接入层（AS）控制面的核心，由 3GPP TS 38.331 定义。RRC 层负责：

    • 广播系统信息（SIB）
    • 寻呼（Paging）管理
    • UE 与网络之间的 RRC 连接建立、维护、释放
    • 安全性（密钥协商、完整性保护、加密）配置
    • 无线承载（Radio Bearer）管理
    • 移动性管理（切换、小区重选）
    • UE 能力上报

    1.1 为什么需要多个 RRC 状态？

    在 4G LTE 中，UE 只有两种 RRC 状态：RRC_IDLE 和 RRC_CONNECTED。当网络在一段时间内检测不到上/下行数据时，就会命令 UE 进入 IDLE 态以节省功耗。

    然而，现代智能手机的应用（即时通讯、推送通知、位置上报等）会非常频繁地发送少量数据，导致 UE 在 IDLE↔CONNECTED 之间高频切换，带来：

    • 大量 RRC 信令开销（每次重新建连需要 Msg1~4 + RRC Setup + 安全激活等流程）
    • 较高时延（从 IDLE 到可以发送用户数据通常需要 50~100 ms 甚至更多）
    • UE 功耗增加

    为此，5G NR 在 R15 引入了第三种状态 RRC_INACTIVE，在 IDLE 与 CONNECTED 之间架起一座「桥梁」，在低功耗的同时保留 AS 上下文，使重新激活连接更快、信令更少。

    注意：RRC_INACTIVE 仅适用于 SA（Standalone）模式，即 UE 连接到 5GC。在 NSA（Non-Standalone，EN-DC，Option 3x）模式下，NR 小区只涉及 RRC_CONNECTED 状态。

    2. RRC_IDLE 状态详解

    2.1 状态定义

    当 UE 未建立 RRC 连接时，处于 RRC_IDLE 状态。此时：

    • UE 没有 AS 上下文（即接入层配置信息）
    • 无 专用无线资源分配
    • UE 不属于任何特定小区（no cell-level registration）
    • 核心网侧，UE 处于 CM-IDLE（Connection Management IDLE）状态

    2.2 UE 行为

    （1）PLMN 选择与小区驻留

    UE 开机后由 NAS 层选择 PLMN，AS 层执行小区选择（Cell Selection），找到合适小区后”驻留（camp on）”该小区，开始监听控制信道。小区选择准则为 S 准则（TS 38.304 §5.2.3.2）：

    （2）系统信息接收

    UE 必须保持对以下系统信息的有效读取：

    系统信息 内容
    MIB 通过 PBCH 广播，含基本系统信息（SFN、子载波间隔等）
    SIB1 小区驻留相关参数、调度其他 SIB 的信息
    SIB2 小区重选通用参数（如 Qrxlevmin、Threshserving 等）
    SIB3 同频邻区重选参数
    SIB4 异频邻区重选参数
    SIB5 E-UTRA 邻区重选参数（若 UE 支持 E-UTRA）

    （3）寻呼监听

    UE 以 DRX（Discontinuous Reception） 方式周期性唤醒，在 Paging Occasion（PO）时监听 PDCCH 上的 P-RNTI，以接收：

    • Paging 消息（承载于 PCCH）：来自核心网的寻呼（CN-initiated Paging），用 5G-S-TMSI 寻址
    • Short Message（直接在 PDCCH 上）：通知系统信息变更或 ETWS/CMAS 公共告警

    DRX 周期由 NAS 层配置，TS 38.304 规定了 Paging DRX 周期（defaultPagingCycle）范围：32、64、128、256 个无线帧（即 320 ms ~ 2560 ms）。

    （4）移动性管理

    UE 自主执行 小区重选（Cell Reselection），无需向网络发送任何信令。重选依赖 R 准则（Ranking Criterion）：

    当邻区 Rn > 服务小区 Rs 持续 Treselection 时间后，UE 重选至邻区。

    （5）上行能力

    在 RRC_IDLE 状态，UE 只能 通过 PRACH 向网络发送信号（用于发起随机接入流程，建立 RRC 连接），不能在 PUSCH 或 PUCCH 上发送数据。

    2.3 进入与离开 IDLE 的触发

    转换方向 触发条件
    CONNECTED → IDLE gNB 发送 RRCRelease（不含 suspendConfig）
    INACTIVE → IDLE 收到 CN-initiated Paging（UE 在 INACTIVE 态收到核心网寻呼后，先回到 IDLE，通知 NAS）
    IDLE → CONNECTED UE 发起随机接入（Msg1→Msg4），完成 RRCSetup 或 RRCResume 流程

    3. RRC_INACTIVE 状态详解

    3.1 设计动机与优势

    RRC_INACTIVE 是 5G NR 的核心创新之一，首次标准化于 R15（TS 38.331 v15.3.0）。其核心设计理念：

    • UE 侧：保存 AS 上下文（类似 IDLE 省电行为，但无需重建连接）
    • 网络侧（gNB）：保存 UE 的 AS 上下文和最后服务小区信息
    • 核心网侧：UE 保持 CM-CONNECTED 状态（与 IDLE 不同！），N2 和 N3 连接维持

    对比 LTE IDLE，RRC_INACTIVE 带来的提升（来自学术分析）：

    指标 提升倍数
    恢复时延 约 8× 优于 LTE IDLE
    功耗效率 约 5× 优于 LTE IDLE
    信令开销 约 3.5× 减少

    3.2 UE 行为

    （1）AS 上下文保留

    UE 在进入 INACTIVE 时保留：

    • 安全上下文（Security Context）：包括 K_gNB、加密/完整性密钥
    • 无线承载配置（Radio Bearer Configuration）
    • 最后服务 gNB 的 UE 上下文标识（I-RNTI）

    （2）标识符：I-RNTI

    网络通过 RRCRelease 消息中的 suspendConfig 为 UE 分配 I-RNTI（Inactive RNTI），用于在非激活态识别 UE 的挂起上下文：

    • fullI-RNTI（40 bit）：完整标识，用于寻呼消息寻址
    • shortI-RNTI（24 bit）：短标识，用于较少比特的场景

    （3）寻呼监听

    与 IDLE 态类似，UE 在 INACTIVE 态也以 DRX 方式监听 PO，但同时监听：

    • CN-initiated Paging（使用 5G-S-TMSI）→ UE 转回 RRC_IDLE，通知 NAS
    • RAN-initiated Paging（使用 fullI-RNTI）→ UE 发起 RRC 连接恢复流程（RRCResumeRequest）

    （4）RNA（RAN Notification Area）管理

    网络在 suspendConfig 中为 UE 配置 RAN 通知区域（RNA），RNA 可以是：

    RNA 规则：

    • RNA 必须包含在 CN 注册区（Tracking Area）之内
    • RNA 可以跨多个小区，也可以只有一个小区

    （5）RNA 更新（RNAU）

    UE 在以下情况必须发起 RAN-Based Notification Area Update（RNAU）：

    • 周期性：t380 定时器超时（可配置范围：5~720 分钟，见 TS 38.331 suspendConfig）
    • 位置变化：UE 重选到一个不在当前 RNA 范围内的小区

    RNAU 流程：UE 通过 PRACH 发送 RRCResumeRequest（resumeCause = rna-Update），收到 RRCRelease（含新的 suspendConfig）后返回 INACTIVE，或收到 RRCResume 后转为 CONNECTED。

    （6）suspendConfig IE 关键字段

    3.3 进入与离开 INACTIVE 的触发

    转换方向 触发消息/条件
    CONNECTED → INACTIVE RRCRelease（含 suspendConfig）
    INACTIVE → CONNECTED RRCResumeRequest → RRCResume（上层数据需求 / RAN Paging）
    INACTIVE → IDLE 收到 CN-initiated Paging；或 UE 选择新 PLMN；或 RRCResume 失败
    INACTIVE → INACTIVE RNAU 完成后网络重新下发 RRCRelease（含 suspendConfig）

    4. RRC_CONNECTED 状态详解

    4.1 状态定义

    当 UE 与 gNB 之间建立了 RRC 连接时，处于 RRC_CONNECTED 状态。此时：

    • UE 有完整的 AS 上下文（安全配置、无线承载、测量配置等）
    • 核心网侧 UE 处于 CM-CONNECTED 状态
    • 存在 N2 信令连接（gNB ↔ AMF）和 N3 用户面连接（gNB ↔ UPF）

    4.2 UE 行为

    （1）数据收发

    UE 可以在分配的无线资源上进行数据传输：

    • 下行：在调度的 PDSCH 上接收数据
    • 上行：通过 SR（Scheduling Request）触发上行授权，在 PUSCH 发送数据

    （2）网络控制移动性

    连接态下，移动性由网络控制：

    • gNB 配置 测量（Measurement）：A1~A6 事件、B1/B2 事件
    • UE 上报测量结果（MeasurementReport）
    • gNB 根据报告决定是否发起 切换（Handover）

    （3）DRX（非连续接收）

    为节省功耗，CONNECTED 态也支持 DRX（TS 38.321）：

    参数 说明
    onDuration 每个 DRX 周期内 UE 激活监听的时隙数
    drx-InactivityTimer 收到 PDCCH 后继续保持激活的计时
    drx-RetransmissionTimerDL/UL HARQ 重传等待时间
    drx-LongCycleStartOffset 长 DRX 周期起始偏移

    （4）SRB 与 DRB

    连接态下存在：

    • SRB0：使用 CCCH，承载 RRCSetupRequest 等初始消息
    • SRB1：使用 DCCH，承载 RRC 信令（PDCP 保护）
    • SRB2：使用 DCCH，承载 NAS 消息（低优先级，在安全激活后建立）
    • DRB1~N：承载用户平面数据（PDU Session 建立后创建）

    4.3 进入与离开 CONNECTED 的触发

    转换方向 触发条件
    IDLE → CONNECTED RRCSetup 完成（新建连接）
    INACTIVE → CONNECTED RRCResume 完成（恢复连接）
    CONNECTED → IDLE RRCRelease（无 suspendConfig）或 RLF（Radio Link Failure）后重建失败
    CONNECTED → INACTIVE RRCRelease（含 suspendConfig）

    6. 三态对比总结

    特性 RRC_IDLE RRC_INACTIVE RRC_CONNECTED
    RRC 连接 无 挂起（Suspended） 建立（Established）
    AS 上下文 无 UE & gNB 均保存 完整保存
    核心网状态 CM-IDLE CM-CONNECTED CM-CONNECTED
    N2/N3 连接 无 维持 维持
    移动性管理 UE 自主重选 UE 自主重选 + RNAU 网络控制切换
    寻呼类型 CN Paging only CN + RAN Paging 不适用（已连接）
    寻呼标识 5G-S-TMSI 5G-S-TMSI / fullI-RNTI —
    数据传输 不可 不可 可以
    唤醒方式 DRX（Paging） DRX（Paging） DRX（PDCCH）
    恢复到 CONNECTED 全新 RRC 建立 快速恢复（Resume） 已在连接态
    适用模式 SA / NSA 仅 SA SA / NSA
    省电能力 高 高 低（取决于 DRX）

    7. UE 能力上报概述

    7.1 为什么需要能力上报？

    5G NR 的 UE 种类繁多——从入门级 RedCap 设备到高端旗舰手机，其支持的频段、天线数量、调制阶数、CA 组合、MIMO 层数、编解码能力等千差万别。网络需要了解 UE 的确切能力，才能：

    • 选择合适的调度策略（MCS、MIMO 层数、CA 配置）
    • 避免下发 UE 无法执行的配置（如 UE 不支持 4 层 MIMO 却下发 4 层配置）
    • 进行资源优化（如网络仅在 UE 支持 256QAM 时才使用高阶调制）

    7.2 相关规范

    规范 内容
    TS 38.331 UECapabilityEnquiry / UECapabilityInformation 消息定义及 UE 过程
    TS 38.306 NR UE 无线接入能力参数（capability parameters）详细定义
    TS 36.331 E-UTRA UE 能力（NSA 场景下 EUTRA-NR 联合能力）
    TS 38.101 NR UE 无线发射接收要求（Band 定义）

    7.3 能力上报的时机

    网络通常在以下时机请求 UE 能力：

    1. 注册流程（Registration）：UE 首次注册时，AMF 可通过 NG 接口向 gNB 指示需要 UE 能力
    2. RRC 建立/恢复后：gNB 在 RRC_CONNECTED 状态下随时发送 UECapabilityEnquiry
    3. 切换前：目标 gNB 可能通过源 gNB 传递 UE 能力，也可重新请求
    4. 能力变更：若 UE 的无线能力发生变化（如插入/拔出外置天线），UE 通过 NAS 层 TAU/Registration 流程通知网络（含 IE ueRadioCapabilityForPaging），网络随后重新请求能力

    优化：网络在首次获取 UE 能力后会本地存储，后续连接不必每次重新请求（除非能力更新）。

    8.2 关键 IE 说明

    （1）UE-CapabilityRAT-RequestList

    列出网络希望 UE 上报能力的 RAT 类型，每个条目包含：

    rat-Type 含义
    nr 纯 NR 能力
    eutra-nr E-UTRA 与 NR 联合能力（NSA/MR-DC 场景）
    eutra 纯 LTE 能力

    （2）UE-CapabilityRequestFilterNR

    这是网络对 UE 上报内容的过滤器，核心字段：

    IE 字段 含义
    frequencyBandListFilter 网络感兴趣的频段列表（强制包含，UE 只上报这些频段的能力）
    requestedMaxCCsDL 网络需要了解的最大下行 CC 数（用于 CA 能力过滤）
    requestedMaxCCsUL 网络需要了解的最大上行 CC 数
    requestedFreqBandsNR-MRDC 针对 MR-DC 的 NR 频段列表
    requestedCapabilityCommon 请求公共能力（如通用 UE 能力参数）

    重要：在 NR 中，frequencyBandListFilter 是强制（mandatory）字段，而在 LTE 中这是可选的。这是 NR 的一个关键优化——网络只请求自己感兴趣频段的能力，大幅减少消息体积。

    10. Feature Sets 与 Feature Set Combinations

    10.1 设计背景

    随着 CA（载波聚合）和 EN-DC（LTE-NR 双连接）的引入，UE 需要上报大量频段组合（Band Combination）下的能力。若对每个频段组合、每个频段分别列出能力参数，消息体积会指数级膨胀（在 LTE-Advanced 时代，部分设备 UE 能力消息已超过 100 KB）。

    Feature Sets 机制从 LTE R15 和 NR R15 开始引入，通过复用解决这一问题。

    10.2 三层结构

    关键规则：

    • 一个 FeatureSet 代表一组 UE 在对应载波上支持的能力
    • 同一个 FeatureSet（由 ID 标识）可以被多个频段组合复用
    • 上行（UL）和下行（DL）Feature Set 分别定义（FeatureSetDownlink / FeatureSetUplink）
    • 每个 CC 的能力进一步细化为 FeatureSetDownlinkPerCC

    10.3 示例：双频 CA 能力上报

    假设 UE 支持 Band n78 + Band n41 的 CA，每个频段都支持相同的能力（100 MHz 带宽、4 层 MIMO、256QAM）：

    不使用 Feature Sets（旧方式）： 需要为每个频段单独列出完整能力参数 × 每个组合 → 大量重复

    使用 Feature Sets（新方式）：

    同一个 FeatureSet（ID=1）被两个频段复用，消息体积大幅减少。

    11. UE 能力上报流程与时序

    11.1 标准流程（TS 38.331 §5.6.1）

    11.2 消息分段传输（RRC Message Segmentation）

    当 UECapabilityInformation 消息体积过大（超过 PDCP SDU 最大尺寸，由 TS 38.323 定义）时，UE 必须启用 RRC 消息分段（UL Message Segmentation） 传输（TS 38.331 §5.7.7）：

    • gNB 在 UECapabilityEnquiry 中通过 IE rrc-SegAllowed 允许分段
    • UE 将 UECapabilityInformation 拆分为多个 RLC SDU，通过 SRB1 上的 AM RLC 模式分段发送
    • gNB 重组后完整解析 UE 能力

    11.3 能力的跨 RAT 一致性要求

    当 UE 同时上报 nr、eutra-nr 等多个 RAT 容器时，TS 38.331 要求：

    UE 应确保所有能力容器中的 Feature Set ID 保持一致性——即以相同 frequencyBandListFilter、requestedMaxCCsDL/UL 等过滤条件查询时，各容器中的 Feature Set 定义应互相对应。

    11.4 能力存储与复用

    • gNB 可将获取到的 UE 能力通过 UE Context 在 Xn 切换时传递给目标 gNB
    • AMF 也可将 UE 能力（以 UERadioCapability IE 形式）存储并在 UE 重连时下发给 gNB，避免重复请求

    12. 小结

    UE 状态机

    5G NR 定义了三种 RRC 状态，形成了一个功耗与响应时延的最优折衷：

    • RRC_IDLE：最省电，无 AS 上下文，移动性完全由 UE 自主控制，重建连接开销最大
    • RRC_INACTIVE：兼顾省电与快速恢复，AS 上下文双端保留，核心网连接不中断，是 5G NR 相对 LTE 的核心创新点之一
    • RRC_CONNECTED：完整数据收发能力，网络控制移动性，功耗最高但时延最低

    RRC_INACTIVE 状态的引入，对于频繁发送少量数据的物联网和移动互联网应用场景，相比 LTE 可带来约 8 倍的时延改善和约 5 倍的功耗改善。

    UE 能力上报

    UE 能力上报机制（TS 38.331 + TS 38.306）解决了多样化终端与网络配置之间的协商问题：

    • UECapabilityEnquiry 通过 frequencyBandListFilter 等过滤器精准请求，减少冗余信息
    • UECapabilityInformation 通过 Feature Sets + Feature Set Combinations 的三层结构避免重复，大幅压缩消息体积
    • 能力信息可在 gNB 和 AMF 侧缓存，避免每次连接都重新请求
